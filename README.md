# ez-v2b-animation

**作者：B站 @高压郭炖大葱**

面向 **VRChat 模型优化**的一键 IK 化工具。把任意常规人形骨架变成可动画的 IK 骨架，
并自带 IK 控制 / 表情 / 面捕三套工具面板。

## 解决的 VRChat 模型痛点

VRChat 模型（VRM / VRChat 导出 / MMD 转换）普遍存在这些问题：

| 痛点 | 具体表现 |
| --- | --- |
| 骨骼命名混乱 | VRChat 标准、VRM 0.x、VRM 1.0、MMD 日文命名混用 |
| 没有 IK | 纯 FK 骨架，摆姿势全靠一根根转骨骼 |
| 手柄命名不可预测 | `LowerLeg.L.003` 这种，靠猜猜不出来 |
| IK 不完整 | 有 IK 但缺链末端旋转、缺控制器、缺分组 |
| 形态键体系不统一 | `vrc.blink_left` / `vrc.blink` / `vrc.Blink` / `まばたき` 四种写法 |
| 贴图路径失效 | FBX 导入后材质变紫 |
| 传文件丢贴图 | 外部引用的贴图不跟着 blend 走 |

```
旧流程：导入 -> 看图猜骨骼名 -> 手工建手柄 -> 手工挂约束 -> 手工建控制器 -> 手工分组
        （每个模型 2~4 小时，且极易出错）

ez 流程：打开文件 -> 在面板里点一下「一键处理」-> 完成（约 3 秒）
```

**换模型不用改代码**：核心是结构发现，不写死任何骨骼名，全部靠约束结构反查。
实测覆盖三套命名规则完全不同的 VRChat 模型。

> 使用、修改、二次分发请保留本署名。

## 一、安装

从本仓库的 Releases 页面下载 `ez_v2b_animation.zip`，然后：

```
Blender > 编辑 > 偏好设置 > 附加组件 > 从磁盘安装 > 选择 ez_v2b_animation.zip
```

勾选启用后，3D 视图按 `N` 键，侧栏出现 **EZ V2B** 标签页，共 6 个面板：

```
EZ V2B
  ├ ez-v2b-animation   骨架列表 + 一键处理 + 只读预检
  │   ├ 处理选项        各项开关（默认 = 保持原有行为）
  │   └ 更新            检查 / 下载 / 安装
  ├ IK / FK 控制        Snap 切换、手柄归位、显隐、扭转传递
  ├ 表情                形态键一键表情、姿势槽
  └ 面部捕捉            摄像头驱动形态键、两段校准、录制烘焙
```

**环境要求**：Blender 4.0 及以上（开发与实测环境为 4.4.3）。

**面捕依赖**（可选，约 94 MB）：面部捕捉需要额外的依赖包，与插件分开分发。
不安装时 IK 控制与表情功能完全不受影响，面捕面板会给出提示与安装入口。

## 二、一键处理做了什么

在面板里选中骨架 → 点「一键处理」→ 11 步全自动，每步都有数值判据：

| 步骤 | 内容 | 判据 |
| --- | --- | --- |
| 1 | **结构发现** | 反查出 IK 约束、手柄、极向、链长、头部 TRACK_TO |
| 2 | **补 IK 手柄与极向** | 缺失时从零建，弯曲侧从 rest 姿态反推 |
| 3 | **IK 约束 + 链末端旋转** | 原模型缺失的自动补（如 Mafuyu 的脚） |
| 4 | **极向角度扫描** | 仅从零建时；默认 0 是错的 |
| 5 | **前臂扭转传递** | `LOCAL/LOCAL` + 只开 Y + `BEFORE` + 0.4 |
| 6 | **Root / Hips 控制器** | 全部控制器挂到根下 |
| 7 | **IKFK 切换器与驱动** | 0 = FK，1 = IK，默认 1.0 |
| 8 | **控制器形状** | 尺寸按**实测世界度量**换算 |
| 9 | **骨骼集合分组** | 控制器 / 切换器 / 主体 / 手指 / 头发 / 装饰 |
| 10 | **写 rig_profile** | 供面板自动发现角色 |
| 11 | **重绑并打包纹理** | 按文件名递归找回贴图，打包进 .blend |
| 12 | **数值验证** | 静置偏差、IK 跟随率、约束完整性 |

**处理前可以先点放大镜（只读预检）**，不修改任何数据，先看清结构。

### 纯 FK 骨架（无 IK）也支持

FBX 导入的模型通常只有纯 FK 骨架。这种情况 ez 会**从零建全套**：

```
从零建手柄 ez_arm_L_ik（head 对齐 Hand.L）与极向 ez_arm_L_pole
从零建手柄 ez_leg_R_ik（head 对齐 Foot.R）与极向 ez_leg_R_pole
从零建头部手柄 ez_head_ik（沿 Head 的 rest 局部 Z 轴偏移 0.30）
从零建 IK: Lower_arm.L <- 手柄 ez_arm_L_ik 极向 ez_arm_L_pole chain=2 pole=-90°
从零建头部追踪: Head <- ez_head_ik（TRACK_TO / TRACK_Z / UP_Y）
```

实测（`verify_from_scratch.py`，把 Mafuyu 退化成纯 FK 后处理）：

```
新建骨骼 15 根 四条链齐全 静置偏差 0.000632 跟随率 0.9684
```

**极向方向必须轴对齐**——这是实测出来的坑：rest 接近伸直时（弯曲深度仅 0.0013），
弯曲方向的倾斜分量是数值噪声被归一化放大出来的（得到 `(0.0008, 0.9357, -0.3529)`
而不是纯 `(0, 1, 0)`），用它会带偏 IK 解算平面、静置偏差飙到 0.002447。
取主导轴做轴对齐后回落到 0.000632。

## 三、核心：结构发现，不写死任何骨骼名

这是能"换模型不改代码"的根本原因。

实测三套命名规则**完全不同**的模型，全部正确识别：

```
模型 手 IK 脚 IK 极向
Karin      (角色.blend)      LHik RHik    LFIK RFik               LHCik LFCik
Chocolate  (角色.blend)      LHIK RHIK    LowerLeg.L.003 RLIK     LWAY RWAY
Mafuyu     (Mafuyu.blend)    LHIK RHIK    Lower_leg.L.001 …       Upper_arm.L.001
```

用命名匹配必然翻车（`LowerLeg.L.003` 当脚 IK 手柄，靠猜猜不出来）。
所以全部靠**约束结构反查**：

```
扫所有骨骼的约束：
  type == IK        -> IK 骨骼 / 手柄 / 极向 / chain_count / pole_angle
  type == TRACK_TO  -> 头部被驱动骨骼 + 头部手柄（自动认出 Headik 这种不规则命名）
  type == COPY_ROTATION 且 subtarget == 手柄 -> 链末端旋转骨骼
```

左右与臂腿的判定：**名字优先，几何兜底**。

## 四、踩过的坑（都实测过，写在代码注释里）

### 尺寸：`matrix_world` 完全不可信

```
模型        matrix_world   to_scale() 真实身高 骨骼本地单位
Karin 单位阵          1.0          1.35       1.44
Chocolate 单位阵          1.0          104.86     456      <- 差 100 倍
Mafuyu 单位阵          1.0          1.42       1.38
```

**三台角色的 `matrix_world` 都是单位阵**，缩放全在骨骼数据里。
按 `to_scale()` 换算会得到 1.0，而 Chocolate 真实身高是 104.86。

更麻烦的是 **Chocolate 是 Y-up 骨架**（身体轴是世界 Y）：

```
脚底 -> 发顶 向量 = (-5.27, 104.42, -8.11) 主导轴 Y，模长 104.86
```

所以：
- 用 `head_local.z` 量身高 → 得到 456（荒谬）
- 用世界 Z 跨度 → 得到 0.18（同样荒谬）
- 用骨骼包围盒 → 含飘带/尾巴，跨度 111
- 用网格包围盒 → 含远离身体的附件（`Kemono_Tail` 到 -34）
- **用脚底→发顶的向量模长** → 正确，且与轴向无关

这套逻辑集中在 `ez_metrics.py`，所有尺寸计算都走它。

### 其他实测坑

| 症状 | 根因 | 解法 |
| --- | --- | --- |
| 移动 IK 手柄骨骼纹丝不动 | 集合在 ViewLayer 里 `exclude=True` | 处理前统一解除 |
| 约束"没生效" | `pose.bones[].head` 本身就含约束结果 | 跟 `bone.head_local` 比 |
| 改完属性驱动不响应 | Python 赋值不触发 depsgraph | `update_tag()` + `view_layer.update()` |
| 编辑模式前后复用 `Bone` 引用 | 层级重建，引用失效 | 退出编辑模式后重新取 |
| 极向放反侧 | 末端位置正确，只有中间关节错 | 从 rest 姿态反推弯曲侧 |
| `pole_angle` 默认 0 | 不是 rest 的弯曲平面 | 扫 9 个角度取最优 |
| 加扭转约束把 T-pose 弄坏 | 用了 `WORLD` 空间 | 改 `LOCAL`，只开 `use_y` |
| 形状对象变成 20 米巨物 | `custom_shape` 素材对象没隐藏 | `hide_viewport=True` |
| 子模块 `import` 失败 | 插件包 / 单文件 / 文本块三种加载方式 | 分层导入兜底 |

## 六·五、纹理重绑与打包

解决 FBX 导入的两个常见痛点：

- **材质变紫**：FBX 里只存文件名，实际贴图在解压目录的 `Textures/` 下
- **换机器丢贴图**：外部引用的贴图不跟着 `.blend` 走

面板里每个角色下方有 **「重绑并打包纹理」** 按钮，也可以在一键处理的选项里开关。
独立操作符支持指定搜索目录，以及"只处理该骨架引用的贴图"（默认开，避免误伤其他角色）。

处理流程：

```
1. 按文件名递归扫描指定目录，建立 {文件名: 真实路径} 索引
2. 逐张重指路径 -> reload
3. 逐张 pack() 进 .blend
4. 报告：重绑几张 / 打包几张 / 哪些找不到 / 打包体积
```

实测（`verify_texture.py`，真实贴图 + 故意打断路径）：

```
重绑 11 张 打包 11 张（28.1 MB） 幂等复跑不再重复打包
文件 10.6 MB -> 38.6 MB（贴图进了 blend）
保存后重开：打包状态持久化，11 张全部可用
按骨架过滤：11 张（该骨架引用） vs 16 张（全场景）—— 不会误伤其他角色
```

**代价与取舍**：打包会让 `.blend` 变大（贴图体积），换来的是换机器/传文件不丢贴图。
不想打包时，操作符里关掉「打包进文件」只做路径重绑即可；也可以点「取消打包」写回磁盘。

## 六·六、上臂/前臂相关（含两个已修缺陷）

### 缺陷一：扭转传递在 `chain_count=2` 的模型上被静默跳过

**症状**：用户报"上臂旋转不生效"，且前臂不跟着手腕扭。

根因（实测）：

```
chain 是"IK 骨骼沿父级向上 chain_count 根"。
chain_count=2 时 chain 只有 [Lowerarm_L, Upperarm_L] 两个元素。
原实现写的是 fa = chain[2] if len(chain) > 2 else None
  -> 越界 -> if not fa: continue  -> **静默跳过**，不报错也不警告。
```

用户的模型正是 `chain_count=2`；Karin 是 3 碰巧有 `chain[2]`，所以之前测试没暴露。

修法：`_forearm_of()` —— IK 约束就挂在前臂上，所以**沿父级找最近的带 IK 约束的骨骼**，
不依赖任何下标。找不到再退回 IK 骨骼自身。两侧都加了"未安装"警告，不再静默。

### 缺陷二：手柄骨长轴没对齐前臂（影响扭转传递效果）

文档实测三台角色的"手柄骨长轴 vs 前臂骨长轴"夹角都 `< 0.5°`。
从零建手柄时我抄的是**末端骨骼**的 tail，实测夹角 **2.638° / 4.223°**——
夹角偏大时 `COPY_ROTATION(LOCAL + 只开 use_y)` 在静置时就不再恒等。

修法：手柄 head 仍落在末端骨骼 head（保证 IK 静置零偏差），
tail 改为**沿前臂骨长轴**伸出，长度取前臂骨长的 60%。

### 缺陷三：面板显示「无前臂骨」（同一个坑的第二、三处）

修完构建器后用户仍报"依旧显示无前臂骨"——因为**面板与操作符里还有两处同样的 `chain[2]`**，
上一轮只改了构建器。

同时查出**第三个坑**：`profile` 的字段语义错位。

```
discover 结果:   ik = Lowerarm_L（IK 骨骼）   handle = ez_arm_L_ik（手柄）
profile 里:      ik = ez_arm_L_ik（手柄！）   chain = [Lowerarm_L, Upperarm_L]
```

原插件（karin）的约定里 `ik` 存的就是**手柄名**，而面板/操作符/构建器都想直接拿"IK 骨骼"。
手柄上没有 IK 约束，拿它去找前臂必然失败。

修法：

```
1. profile 同时写全三个字段，兼容两种读法
     "ik"      = 手柄骨骼名（与原插件一致，Snap 等操作符按此读取）
     "handle"  = 同值，语义更清晰的新名字
     "ik_bone" = IK 约束所在骨骼（扭转传递的挂载点）
2. _ez_forearm() 五层解析，兼容所有历史 profile
     1. ik_bone
     2. chain[0]（chain 首项 = IK 骨骼）
     3. ik 当骨骼名试（若它带 IK 约束就是 IK 骨骼）
     4. ik 当手柄名，在场景里反查哪个骨骼的 IK 约束指向它
     5. 都失败 -> None，调用方给提示
3. 面板与操作符统一改用 _ez_forearm
```

**第四个坑**：移植切片起点错了。

```
TWIST_CNAME / TWIST_DEFAULT 定义在原始文件第 166 行，
而切片从 191 行起 —— 常量定义整个丢了，
于是移植块里到处引用 TWIST_CNAME 却没有定义，面板一读就 AttributeError。
```

修法：切片起点改到 166（覆盖常量），但**不取 160**——170-188 的 `_rig` / `_has_switch`
与 `ez_bridge` 里的同名函数重复，切进来会覆盖桥接层。

实测验证（`verify_forearm.py`）：

```
四套模型的前臂定位全部成功:
 用户模型  chain_count=2 -> Lowerarm_L / Lowerarm_R
  Mafuyu / Karin / Chocolate  chain_count=3 -> 各自前臂

用户模型处理后，模拟面板读取:
  L 臂: _ez_forearm -> Lowerarm_L      <- 不再是手柄
 扭转传递 = 已安装，influence=1.00 面板显示 100%
  R 臂: 同上

对照（证明修复必要）:
 旧写法 chain[2] 在这份 profile 上 -> None -> 面板显示「无前臂骨」
```

### 测试方法上的两个坑（都踩过）

```
1. 对比"扭转开/关"必须用 constraint.mute，不能改 influence
   —— influence 被驱动接管，手动赋值会被立刻覆盖，
 两次测到同一状态，恒得 0.000000。连已知正常的 Karin 也会误判。

2. 保存必须在"打开原文件做对照"之前
   —— open_mainfile 会把 build 的结果整个丢掉，
 保存下来的是原模型，重开后自然"找不到扭转传递"。
```

### 关于"上臂转不动"

`IKFK = 1.0`（IK 模式）时，IK 约束 `chain=2` **同时接管上臂与小臂**，
手动转上臂不动是**正常行为**。要手动摆姿势请先切 FK：

```
IKFK = 0 (FK): 上臂转 40° -> 末端位移 0.006212 有效
IKFK = 1 (IK): 上臂转 40° -> 末端位移 0.000000 由 IK 接管（正常）
```

面板的「IK / FK 控制」里有 Snap 按钮，切换时不会跳变。

## 七、面部捕捉

```
摄像头 → mediapipe FaceLandmarker → 52 个 ARKit blendshape + 4×4 头部矩阵
      → 逻辑通道映射 → One Euro 滤波 → 写形态键（实时）或写缓冲（录制）
      → 自适应抽帧烘焙成关键帧
```

要点：

- **头部是位置驱动**：`TRACK_TO` 让头部指向手柄位置，`offset = D × tan(θ)`，`M` 与 `D` 运行时标定
- **歪头（roll）**：`TRACK_TO` 原生只有 pitch/yaw 两个自由度，roll 靠 `Head` 上一条 `COPY_ROTATION(mix=ADD, 只开 Z)` 补出来，精度 `< 0.03°`
- **两段校准**：`neutral(2s) → gap1(2s) → closed(2s) → gap2(1s)`，去掉静息偏置并归一化满值
- **摄像头必须在主线程打开**：MSMF 在 worker 线程 `opened=True` 但读不出帧（COM 每线程初始化）

### 摄像头稳定性（三个已修缺陷）

**缺陷一：卡在启动摄像头**

只看 `isOpened()` 就认定可用，但实测 `isOpened()==True` 而 `read()==False` 很常见，
于是锁死在一个读不出帧的摄像头上。且三个后端在单个 timer 回调里串行尝试，
最坏冻结主线程 15 秒、无取消入口。

```
修法：判定标准改成「实际读到一帧」（连读 3 次）
 后端逐 tick 推进，主线程单次最多冻一个后端
 总超时 25 秒 + 面板进度 + 「取消打开」按钮
```

**缺陷二：运行中断流（用一会儿突然不动）**

```
OnReadSample() is called with error status: -1072873821
-1072873821 = 0xC00D36C3 = MF_E_VIDEO_RECORDING_DEVICE_INVALIDATED
```

Windows 把设备判为失效（被其他程序抢占 / 休眠唤醒 / USB 抖动）。
原实现只会一直 read 到 90 次然后报错。

```
修法：连续失败 30 帧 -> 释放旧句柄 -> 自动重连（最多 3 次）
 读到帧即清零计数；超过上限明确报错停止
```

**缺陷三：设备被反复 reopen（这个是我自己引入的）**

第一版修复里，找到可用后端后**继续尝试后续后端**，每次都 release 上一个候选。
MSMF 用异步回调（`SourceReaderCB::OnReadSample`），同一设备被反复打开又释放
会让它的流被系统判为失效 —— 正是上面那个 `0xC00D36C3`。

```
修法：一旦找到可用后端就立即定案，不再试后面的
```

实测验证（`verify_camera.py`，用假摄像头驱动状态机，7 个场景）：

```
场景A  MSMF(打不开) -> ANY(可用)    3 个 tick 后切换，MSMF 已释放
场景B 三后端全失败 明确报错，不无限等
场景C 模拟超时                     25 秒后报错停止
场景D 打开途中取消 立即回 idle
场景E 运行中断流                   30 帧后自动重连，句柄已释放
场景F 反复断流超过上限 停止并说明原因
场景G 重连后恢复 计数清零
```

### 形态键通道解析（VRM 命名）

四套命名体系都要覆盖（`ez_discovery.py` 的 `CHANNEL_ALIASES`）：

```
旧版 VRChat   vrc.blink_left / vrc.looking_up / VRC.v_aa
VRM 0.x       vrc.blink / vrc.looking_up / vrc.v_aa
VRM 1.0 标准  vrc.Blink / vrc.Looking Up / vrc.Looking Down   <- 首字母大写 + 带空格
MMD 日文      まばたき / 笑い / ウィンク / 口角上げ
```

**踩过的坑**：候选表漏了 VRM 1.0 那套（带空格的），精确匹配全不命中，
于是走模糊兜底（关键词包含 + 取最短），把 `blink_left` / `blink_right`
**都兜到了同一个 `vrc.Blink` 上** —— 表现为眨眼时左右眼同步动，
`look_up` / `look_down` 落到幅度极小的键上（0.00075），用户感觉"不稳定"。

修法两条：

```
1. 归一化匹配：去空格/下划线/点 + 转小写
   'vrc.Looking Up' 与 'vrc.looking_up' 归一到同一个 key，一张表覆盖两套命名
2. 去重：一个键被多个通道占用时只保留第一个，其余回退次优候选
 宁可某个通道缺，也不要两个通道打架
```

实测（`verify_channels.py`，含用户的模型）：

```
用户模型 (VRM 1.0)   18 通道，左右眼指向不同的键
Karin (旧版 VRChat)  blink_left / blink_right 分开
Chocolate (VRM 0.x) 单 blink 键，左右共用（模型本身如此）
Mafuyu 回归通过，无重复占用
```

### 依赖部署（重要）

面捕依赖 **93.9 MB（解压后 250.8 MB / 1557 文件）**，与主插件（约 116 KB）**分开分发**。
主插件保持小体积便于频繁更新，依赖只在首次安装时下一次。

| 文件 | 大小 | 说明 |
| --- | --- | --- |
| `ez_v2b_animation.zip` | 约 116 KB | 插件本体，从磁盘安装 |
| `ez_v2b_animation_single.py` | 约 147 KB | 单文件版，供文本块或快速分发 |
| `ez_v2b_facecap_deps.zip` | 93.9 MB | 面捕依赖，解压即用 |
| `SHA256SUMS.txt` | 200 字节 | 校验和 |

全部产物都在 [Releases](../../releases/latest) 页面下载。

**安装依赖（三选一）**：

1. **从 zip 部署**（推荐）：`EZ V2B` → 面部捕捉面板 → 顶部「安装面捕依赖」→ 选「从指定目录/zip 部署」→ 选 `ez_v2b_facecap_deps.zip`
2. **手动解压**：把 zip 解压到插件目录下，得到 `<插件目录>/_blpy_nodeps/`，然后点「重新检查」
3. **自动查找**：点「安装面捕依赖」→ 选「自动查找并部署」，扫描常见位置并复制过来

插件会自动在以下位置找依赖（按优先级，**全部相对推导、零绝对路径**）：

```
1. 面板里手动指定的路径
2. <插件目录>/_blpy_nodeps                        <- zip 解压到这里，推荐
3. <插件目录的兄弟目录>/_blpy_nodeps
4. <Blender 用户 addons>/_blpy_nodeps
5. <Blender 用户目录>/ez_v2b_facecap_deps
6. <当前工作目录>/_blpy_nodeps
```

**依赖内容与红线**（打包脚本内置自检）：

```
 cv2 5.0.0            138.0 MB 抓帧
 mediapipe 1.0.1       54.4 MB 推理
 face_landmarker.task   3.6 MB 模型
 matplotlib            21.3 MB   mediapipe 的硬依赖，删了会 ModuleNotFoundError
 PIL / fontTools       25.2 MB   matplotlib 的下游
 numpy                           **绝不能包含** —— 会顶掉 Blender 自带的 1.26.4
```

**校验下载的文件**：

```bash
sha256sum -c SHA256SUMS.txt
```

Windows 上可以用：

```powershell
Get-FileHash ez_v2b_animation.zip -Algorithm SHA256
```

对照 `SHA256SUMS.txt` 里的值即可。

> **注意**：`SHA256SUMS.txt` 里的哈希是对 **Release 页面上的产物**计算的。
> Release 里的 zip 由 CI 重新构建，与本地开发目录的产物不是同一份文件，
> 哈希自然也不同。核对时请以下载到的文件为准。

> **踩过的坑**：原开发版把 `FACECAP_HOME = r"D:\...\karin_ik_tools"`（开发机绝对路径）
> 写进了代码，并且放在查找顺序第一位。本地开发时能跑，**分发给用户后必然失效**——
> 这就是"分发版摄像头起不来"的根因。现已彻底移除，打包脚本加了红线自检：
> 分发包里出现任何开发机绝对路径一律判为致命缺陷、拒绝出包。

**依赖是可选的**：没装依赖时面捕面板给出提示，IK 控制与表情功能完全不受影响。

## 八、自动更新

三种更新源，优先级从高到低：

1. **清单 URL**（面板可改）—— 返回 JSON
2. **GitHub 仓库** —— 填 `owner/repo`，走 `releases/latest`
3. **本地 ZIP** —— 离线场景

```json
{
  "version": "1.1.0",
  "url": "https://example.com/ez_v2b_animation.zip",
  "notes": "更新说明",
  "channels": {
    "stable": { "version": "1.1.0", "url": "..." },
    "beta":   { "version": "1.2.0b1", "url": "..." }
  }
}
```

**安装流程**：检查 → 下载到临时目录 → 校验 zip 完整性 + 比对包内版本 → 暂存 → 重启 Blender 生效。

为什么不直接替换：Windows 上正在运行的 `.py` 文件被占用，写入会失败。
所以是"暂存 + 重启生效"，安装前会自动备份旧版到 `<addon>.bak.<version>`。

面板上的「立即应用已暂存的更新」用于手动触发替换。

**网络失败绝不阻断主功能** —— 所有更新函数吞异常并返回结果对象。

## 十一、已知限制

- **极向角度扫描**只在从零建 IK 时执行。已有 IK 的模型保留其原有 `pole_angle`，遵循默认行为不变原则。
- **面捕依赖**需单独部署（约 94 MB）。未部署时面捕面板会提示，IK 控制与表情功能不受影响。
- **`TRACK_TO` 原生只有 2 个自由度**，歪头是补出来的，见第七节。
- **直腿 rest 的模型**拖 Hips 时脚会被带离地面，这是直腿几何的固有结果，先把 Hips 往下压一点让膝盖弯出余量即可。
- 面捕的实时手感与延迟需要真实摄像头体感验收，面板已留方向开关。
